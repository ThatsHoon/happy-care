## 1. 행복이란? 무슨 의의가 있는가

### 문제 — 세워둔 보행기는 아무것도 못 한다

국내 65세 이상 인구는 1,051만 명(전체 20.3%)으로 초고령사회에 진입했고, 이 중 독거노인 가구는 36.8%에 달한다. 이 인구가 마주한 두 위험은 통계로 이미 뚜렷하다:

- **낙상**: 고령자 안전사고의 62.7%, 70세 이상 낙상 환자는 10년간 2.1배 증가
- **고독사**: 2024년 사망자 3,924명(전년 대비 7.2% 증가) — 위급상황을 스스로 알리지 못한 채 방치

기존 보행기는 걷는 동안의 이동 보조에만 집중한다. 문제는 **낙상 최다 장소가 화장실·침실**이라는 점 — 정작 위험한 순간엔 보행기가 현관에 세워져 있다. *세워둔 보행기는 그 순간 아무것도 하지 못한다.*

### 해법 — "세워둠"을 약점에서 자산으로

행복이는 이 공백을 없애기 위해, 보행기라는 형태를 유지하면서 **충전 스테이션에 세워두는 행위 자체를 감시 기능으로 전환**한다.

| | 실외 모드 (보행 중) | 실내 모드 (도킹·충전 중) |
|---|---|---|
| 역할 | 이동 보조 (mobility) | 방을 지키는 감시자 (sentinel) |
| 주 센서 | AI Vision·IMU·그립 심박 | 레이더 (카메라 OFF) |

걸을 땐 곁에서 보조하고, 세워둘 땐 방을 감시한다 — **24시간 돌봄 공백이 사라진다.** 부가적으로, 도킹 시 자율추종용 카메라가 물리적으로 꺼지고 레이더만 켜지므로 "사생활 공간에선 보지 않는다"가 소프트웨어 정책이 아니라 **모드 전환으로 물리적으로 보장**된다 — 실내 카메라 감시에 대한 거부감 문제를 구조적으로 해소한다.

## 2. 행복이의 주요 기능 및 워크플로우

### 2.1 공통 두뇌, 두 개의 모드

행복이는 하나의 컴퓨트(보행기 탑재)가 실외·실내 두 모드를 겸하며, **충전 전류/접점 감지**가 유일한 전환 트리거다.

```
[실외 모드] ──(도킹·충전 감지)──▶  전환: 카메라 OFF · 레이더 ON · 실내 판단 활성
[실내 모드] ──(도킹 해제)──────▶  전환: 레이더 OFF · 카메라 ON · 자율추종 활성
```

경계 처리: 도킹 직후 레이더 워밍업(재실 캘리브레이션), 해제 직후 자율추종 재획득, 충전전류 디바운스로 오작동 방지.

### 2.2 실외 모드 — 이동 보조

- **자율추종**: AI Vision으로 보호자 없이 2~5m 거리 유지 동행
- **보행보조**: IMU로 경사·부하 감지, 전동 구동으로 근력 보조
- **낙상 감지**: IMU 기반, 보행 중 낙상을 즉시 포착
- **응급 알림**: 그립 전극으로 상시 심박 측정, 이상 시 보호자·119 자동 연동

### 2.3 실내 모드 — 무구속 레이더 케어

핵심 원리: 낙상·생체·고독사는 별개 기능이 아니라 **하나의 레이더 신호에서 추정한 '사람 상태'를 세 각도로 읽는 것**이다.

| 판단 레이어 | 방식 | 출력 |
|---|---|---|
| 낙상 | micro-Doppler 스펙트로그램 → CNN(주경로) + Range-Angle 규칙(폴백) | `{fall, confidence, 유형}` |
| 생명징후 | 정지 시 흉부 미세변위 → 호흡·심박. 움직임 중엔 "측정불가" 정직 표기 | `{resp_bpm, heart_bpm}` |
| 고독사 | 재실+무동작 시간 누적 → 주의→무생체→위험→자동신고 (외출은 정상) | `{status, 무동작시간}` |

카메라 없이 전파 반사만으로 판단하므로, 화장실·침실 등 사생활이 가장 중요한 공간에서도 거부감 없이 상시 감시가 가능하다.

### 2.4 공통 서비스 계층

이벤트(낙상·생체이상·고독사 경보) → 보호자 앱 실시간 알림(단계적 에스컬레이션, 위험 시 119) + 관제 대시보드(현재 모드·이벤트 타임라인) + 돌봄진단 리포트(활동량·수면·호흡 장기추세로 건강악화 조기경보).

## 3. 워크플로우 상의 각 단계를 어떻게 구현할 것인가

> 8주 PoC의 실제 산출물은 **Gazebo 시뮬레이션이 더미 센서 데이터를 대체 → 탐지 스택 처리 → 웹앱 실시간 시각화**하는 sim→web 파이프라인이다. 물리 하드웨어(§4)는 실물 검증용이며, 개발의 본체는 소프트웨어다.

### 3.1 검증 원칙 — "탐지 스택은 sim/real 무관"

Gazebo Classic 11엔 mmWave 레이더 센서가 없다. 그래서 Gazebo는 물리·지상진실(위치·속도·접촉)만 제공하고, **커스텀 sim-radar 역할을 하는 WorldPlugin**이 실제 파이프라인과 동일한 스키마(`PersonState`/`CareEvent`)를 합성한다 — 탐지 스택·웹앱 입장에선 데이터가 시뮬레이션에서 왔는지 실물 레이더에서 왔는지 구분할 필요가 없다. 이 원칙 덕분에 실물 하드웨어 없이 히어로 데모(도킹→전환→낙상→감지→알림) 전체를 end-to-end로 시연할 수 있다.

### 3.2 관리자가 시나리오를 직접 조종

로봇을 미리 짜둔 스크립트로 재생하는 대신, **관리자 콘솔(`/admin`)에서 웹 텔레옵으로 로봇을 실시간 조종**하고, 낙상·자율추종 등 시나리오를 버튼으로 직접 트리거한다.

```
[관리자 콘솔] ── 텔레옵(WebSocket, WASD+버튼) ──▶ 로봇 /cmd_vel (Gazebo 물리로 실제 이동)
             ── 시나리오 클릭(낙상/자율추종/기타) ──▶ 액터 포즈 전환 (5초 후 자동 회복)
             ◀── 로봇 1인칭 카메라(MJPEG, web_video_server) ── 실시간 시야로 조종
```

로봇의 위치·속도·도킹거리는 항상 Gazebo 물리에서 나온 실측값이고, 액터의 활동 종류(걷기/낙상/정지)는 관리자가 고른 시나리오 라벨이다 — 이 둘이 결합해 실제 `PersonState`가 만들어진다.

### 3.3 도킹 감지 → 모드 전환 (실측 기반)

로봇↔충전스테이션 거리가 0.3m 이내로 1초 이상 유지되면 자동으로 실내 모드 전환 — §2.1의 전환 로직이 타이머가 아니라 **진짜 시뮬레이션 좌표**로 동작한다.

### 3.4 데이터 흐름 (백엔드~프론트엔드)

```
Gazebo WorldPlugin(C++, ground-truth 발행)
   → gazebo_source.py(rclpy 브릿지, 순수 판단로직/IO 분리) — 기존 dummy_source.py 대체
   → EventBus → FastAPI /ws WebSocket
   → 키오스크(/kiosk, 어르신 대면) · 대시보드(/dashboard, 보호자) · 관리자 콘솔(/admin)
```

`contracts.py`의 `PersonState`/`CareEvent` 스키마는 무변경 — 관리자 콘솔 HUD용 `RobotTelemetry` 1개만 신규 추가. Gazebo가 없는 개발 환경에서는 백엔드가 자동으로 `dummy_source.py`로 폴백해 팀원 온보딩이 깨지지 않는다.

### 3.5 프론트엔드 스택

Vite + React SPA(Next.js 대비 SSR 오버헤드 0, roslibjs·Three.js 등 JS 시각화 생태계에 네이티브). 고빈도 스트림(포인트클라우드·카메라)은 Canvas/WebGL 명령형 렌더, 저빈도 UI만 React state — "부드러움의 핵심은 프레임워크가 아니라 렌더링 전략"이라는 원칙.

### 3.6 다음 단계 (이번 PoC 범위 밖)

micro-Doppler CNN 낙상 모델 학습(공개 데이터셋 사전학습 + 자체수집 파인튜닝), 생체 실측 추정, 고독사 상태머신, 실물 레이더 연동 검증.

## 4. 실 제품 제조 시의 하드웨어 구축 자료 디테일

> PoC는 Gazebo 시뮬레이션으로 검증하지만, 실제 양산형 제품은 아래 하드웨어 스택으로 구성된다.

### 4.1 실외 모드 하드웨어

| 계층 | 구성 | 역할 |
|---|---|---|
| 인지·위치추정 | AI Vision 카메라 | 사용자 1차 인식·추종(2~5m), 가림 상황 대응 |
| | IMU | 낙상 감지, 경사·부하 인지 |
| | 스테인리스 그립 전극(손잡이) | 상시 심박 측정 |
| | UWB | 2차 정밀 측위(사각지대 보완) |
| 구동 | 소형 4륜 전동 구동 모듈 | 근력 보조, 파워 어시스트 |
| | 개방형 짐칸(펼치면 의자) | 15~20kg(쌀 한 포대 수준) 적재 |
| 엣지 컴퓨트 | Jetson급 온디바이스 보드 | AI Vision·판단·주행제어 온보드 처리 — 통신 두절에도 상시 동작 |
| 인터페이스 | 손잡이 안쪽 터치 디스플레이 + 음성 인식/TTS | 조작성 확보(노인 UI 원칙: 큰 터치타깃·고대비·음성 우선) |
| 프레임 | 알루미늄 저가 보행기 프레임 기반 | 제조원가 최소화, 복지용구 현장 즉시 적용성 |

### 4.2 실내 모드 하드웨어

| 항목 | 사양 | 비고 |
|---|---|---|
| 레이더 칩 | Infineon **BGT60TR13C** | 60GHz FMCW, 대역폭 ~5.5GHz(거리분해능 ≈3cm), 1Tx+3Rx(L배치) |
| 개발 키트 | **CY8CKIT-062S2-AI** 1~2대 | 온보드 PSoC6 + Imagimob 경량모델 탑재 |
| 각분해능 제약 | ~50°, FoV ±45°, Rx 2개/평면 | TI IWR6843식 조밀 포인트클라우드 불가 → 낙상 주경로를 micro-Doppler CNN으로 확정(설계 근거) |
| 충전 스테이션 | 도킹 접점 + 충전 회로 간이 제작 | 실내 감시 정위치(거실·침실 등 주 생활공간) 겸용 |
| 온보드 추론 | PSoC6 + Imagimob | Jetson 없이 저비용 엣지 AI, INT8 양자화 |

### 4.3 비용 개요 (PoC 기준)

| 계층 | 비용 |
|---|---|
| 보행기(실외) | 기존 행복이 자산 재사용 |
| 실내 인지(CY8CKIT×1~2) | 8–20만원 |
| 충전 스테이션 간이 제작 | 수만원 |
| ML 학습(PC/무료 Colab) | $0 |
| 서비스(클라우드 무료티어) | ~$0 |

양산 로드맵: 개발 단계는 AI 키트 기반, 양산 시 레이더·엣지AI를 단품칩 커스텀 모듈로 전환해 단가를 1/N로 절감.

### 4.4 통신·양산 설계 원칙

- **온디바이스 처리**: 실외(Jetson급)·실내(PSoC6) 모두 엣지에서 1차 판단 완료 → 통신 두절 시에도 안전 기능(낙상 감지·응급 알림)은 상시 동작, 클라우드는 알림 릴레이·장기 기록 용도로만 사용
- **저비용 프레임**: 알루미늄 보행기 수준 저가 설계로 복지용구 현장 즉시 적용성 확보
- **모듈 교체 전제**: PoC의 Gazebo sim-radar → 실물 BGT60TR13C, 더미 심박값 → 실제 그립 전극 신호로 교체될 때 `contracts.py` 스키마(`PersonState`/`CareEvent`)가 그대로 유지되도록 설계 — 시뮬레이션에서 실물로의 전환이 소프트웨어 재작성 없이 이뤄지는 것이 이 아키텍처의 핵심 목표
