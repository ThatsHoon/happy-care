## 0. 근원 — 병합이 균열을 메운다

기존 행복이(보행기)의 약점은 **상시성**이었다. 낙상 최다 장소인 화장실·침실에서 쓰러질 때 보행기는 현관에 세워져 있고, 고독사는 집 안에서 방치된다 — 즉 *세워둔 보행기는 그 순간 아무것도 못 한다.*

**듀얼모드는 이 "세워둠"을 약점에서 자산으로 뒤집는다.**

| | 실외 모드 (보행 중) | 실내 모드 (도킹·충전 중) |
|---|---|---|
| 역할 | 이동 보조 (mobility) | 방을 지키는 감시자 (sentinel) |
| 주 센서 | AI Vision(자율추종)·IMU·그립 심박 | **레이더 (카메라 OFF)** |
| 기능 | 자율추종·보행보조·응급 | 낙상·생명징후·고독사 감지 |

→ **걸을 땐 곁에서 보조하고, 세워둘 땐 방을 감시한다.** 24시간 공백이 사라진다. "세워둠 = 꺼짐"이 아니라 "세워둠 = 감시 켜짐."

**프라이버시 강화**: 사생활 공간(집)에 들어와 도킹하면 **자율추종용 카메라가 꺼지고 레이더만 켜진다.** "실내에선 보지 않는다"가 모드 전환으로 물리적으로 보장된다.

### 브레인스토밍 확정사항

| 항목 | 결정 |
|---|---|
| 제품 | 행복이 (보행기 그대로 유지) + 충전 스테이션 |
| 구조 | **듀얼모드** — 도킹/충전이 실외↔실내 전환 트리거 |
| 라이브 데모 히어로 | **도킹 → 실내모드 전환 → 낙상 감지** 순간 |
| 실외 보행 기능 | 요약·재현(기존 행복이 자산 활용, 풀 라이브 아님) |
| 실내 센서 | mmWave 레이더 단일 (무구속·프라이버시) |
| 실내 하드웨어 | Infineon CY8CKIT-062S2-AI (BGT60TR13C) |
| 실내 서비스 | 실시간 안전망 + 돌봄진단 |

## 1. 시스템 개요 — 듀얼모드

> **구현 스코프 (중요)**: 물리 센서/BOM은 **하드웨어 설명력(제안서 서사)** 용이다. 실제 8주 구현의 본체는 **Gazebo가 더미 센서 데이터를 주입 → 탐지 스택 처리 → 웹앱 실시간 시각화**하는 sim→web 파이프라인이다. 즉 산출물 3축 = ①Gazebo 시뮬(+sim-radar 플러그인), ②탐지 스택(낙상 CNN·생체·고독사·모드전환), ③실시간 웹 시각화(키오스크+대시보드). 실물 레이더는 선택적 검증용.

```
        ┌──────────────── 행복이 (공통 두뇌: CY8CKIT / 보행기 컴퓨트) ────────────────┐
        │                                                                          │
   [실외 모드]                    ─── 도킹 감지(충전전류) ───▶            [실내 모드]
   보행 중                          모드 전환 상태머신                   충전 스테이션 거치 중
   ├ AI Vision 자율추종            (실외 ⇄ 실내)                        ├ 레이더 낙상 감지
   ├ IMU 보행보조·낙상            카메라 ON⇄OFF · 레이더 OFF⇄ON        ├ 레이더 생명징후
   ├ 그립 전극 심박                                                     ├ 고독사 상태머신
   └ 응급 알림                                                          └ (카메라 OFF)
        │                                                                          │
        └────────────────────── 공통 서비스: 대시보드·알림·돌봄진단 ─────────────────┘
                                          (WiFi → 클라우드)
```

**전환 트리거**: 충전 스테이션 접점 접촉 + 충전 전류 감지 → 실내 모드 진입 / 도킹 해제 → 실외 모드 복귀. 소프트웨어 상태머신이 센서·기능 세트를 스위칭.

## 2. 실내 모드 — 인지 계층 (레이더 공통 코어)

> 핵심 원리: 낙상·생체·고독사는 별개 문제가 아니라 **하나의 레이더 신호에서 추정한 '사람 상태'를 세 각도로 읽는 것**. 공통 인지코어 1개 + 판단 레이어 3개.

### 2.1 센서: Infineon BGT60TR13C
- 60GHz FMCW, 대역폭 ~5.5GHz → 거리분해능 ≈ 3cm
- 1 Tx + 3 Rx(L배치) → 방위·고도각 → 사람 3D 위치
- 도킹 시 레이더가 방(주 생활공간)을 향하도록 스테이션 정위치

### 2.2 raw → 표현형
프레임 = 원시 큐브 `[chirps, Rx=3, ADC samples]`. 시간축으로 쌓아 파생:

| 표현형 | 계산 | 용도 |
|---|---|---|
| Range-Doppler Map | 샘플FFT+chirpFFT | 낙상 속도, 재실 |
| **Micro-Doppler 스펙트로그램** | 느린시간 STFT | **낙상(정석)**, 활동분류 |
| Point Cloud (x,y,z,v,snr) | +각도FFT | 낙상 높이급강하, 위치·자세 |
| 미세변위 신호 | range-bin 위상 | 호흡·심박 |

> 원칙: raw로 저장하고 표현형은 오프라인 파생.

## 3. 실내 모드 — 판단 레이어

> **v3 비판검토 반영**: BGT60TR13C는 각분해능 ~50°·FoV ±45°·Rx 2개/평면이라 **TI IWR6843식 조밀 포인트클라우드를 못 낸다**(Range-Doppler·Range-Angle 맵만). 따라서 TI 데이터셋의 "포인트클라우드 높이급강하" 규칙은 우리 칩에 전이되지 않음 → **낙상 주경로를 micro-Doppler CNN으로 확정**, 폴백은 Range-Angle 맵 기반 규칙으로 재정의. 또한 낙상(고프레임·넓은 도플러)과 생체(느린 chirp·위상 안정)는 chirp 설정이 상충 → **시분할 프로파일(낙상↔생체 교대)** 로 준동시 처리.

- **낙상**: **micro-Doppler 스펙트로그램 → CNN (주경로 확정)** + Range-Angle 맵의 고도성분 급변·Doppler 급증 규칙(폴백/앙상블). 출력 `{fall, confidence, 유형}`
- **생명징후**: 정지 시 미세변위 → 호흡(0.1–0.5Hz)·심박(0.8–2.5Hz). 움직임 중 "측정불가" 정직표기. 출력 `{resp_bpm, heart_bpm, 신뢰구간}`
- **고독사**: 같은 사람-상태를 시간축으로. 재실+무동작 N시간→주의→무생체→위험→자동신고. 외출(미재실)=정상. 출력 `{status, 무동작시간, 마지막생체}`

## 4. 도킹 & 모드 전환 (신규 핵심)

- **충전 스테이션(간이 제작)**: 전원 공급 + 도킹 접점 + 실내 감시 정위치. 거실/침실 등 주 생활공간에 배치.
- **도킹 감지**: 충전 전류/접점 신호 → 실내 모드 진입. 해제 시 실외 복귀.
- **전환 로직(상태머신)**:
  ```
  실외모드 ──(도킹·충전 감지)──▶ 전환: 카메라 OFF, 레이더 ON, 실내 판단 활성
  실내모드 ──(도킹 해제)──▶     전환: 레이더 OFF, 카메라 ON, 자율추종 활성
  ```
- **경계 처리**: 도킹 직후 워밍업(레이더 재실 캘리브레이션), 해제 직후 자율추종 재획득. 오작동 방지 디바운스.

## 5. 공통 서비스 계층

- **실시간 알림**: 이벤트 → 보호자 앱 푸시 + (위험 시) 119/지자체. 단계적 에스컬레이션.
- **관제 대시보드**: 현재 모드(실외/실내) 표시, 원룸 맵·이벤트 타임라인, 포인트클라우드 스냅샷(카메라 아님).
- **돌봄진단 리포트**: 활동량·수면·호흡·보행속도 장기추세 → 건강악화·낙상위험 조기경보. 장기데이터는 8주라 **시뮬레이션 재현**.
- 스택: 클라우드 무료티어(Render/Supabase/Firebase), 프론트 Next.js, 백엔드 FastAPI, WiFi 직송.

## 6. 데이터 전략 & 실측 카탈로그 ★

> **배포 가능한 사전학습 모델은 HuggingFace에 사실상 0개**(12키워드 검색). → 우리가 학습(피칭 플러스). 아래는 **블루프린트·사전학습·검증 보조**. 대부분 TI 레이더지만 우리 Infineon과 **같은 60GHz**라 표현형 전이 가능, 도메인 갭은 자체수집으로.

| 기능 | 데이터셋 | 실측 스키마 | 라이선스 | 용도 |
|---|---|---|---|---|
| 낙상 | **GitHub** sareebali/mmwave-radar-fall-detection | 포인트클라우드 `frame,x,y,z,v,snr,noise` · 102 CSV · TI IWR6843 60GHz | ⚠️미표기 | 블루프린트(데이터→학습→데모 공개) |
| 낙상/활동 | strikersoft/microDopplerHAR | `20×1024 float32` 스펙트로그램 · 라벨 1850:63(극불균형) | **MIT** | 사전학습 |
| 심박 | YShane11/mmwave-heart-rate-dataset | 레이더변위 5Hz + ECG 150Hz · 주석헤더 메타 | ⚠️미표기 | 심박 정답쌍 |
| 생체 | rushai-dev/fmcw-vital-signs | `index,breath_phase,heart_phase,label` | **Apache-2.0** | 위상분리 보조 |

**⚠️ 함정 2개**: ① HF 낙상 미러(`SachitanandAgalduti/…`)는 56바이트 깨진 스텁 → GitHub 원본 `GatheredData/`에서 받을 것. ② microDoppler 양성 63개 극불균형 → focal loss/오버샘플링 필수.

### 활용 코드

import pandas as pd, numpy as np

# ③ 심박: 레이더변위 ↔ ECG (주석헤더 스킵)

| TI↔Infineon 도메인 갭 | 블루프린트 복제 후 자체 데이터 파인튜닝 |
| 모드 전환 오작동 | 충전전류 디바운스 + 워밍업/재획득 시퀀스 |
| 심박 라이브 불안정 | 정지 한정 + "측정불가" 표기, 낙상을 히어로로 |
| HW 리드타임 | 발주 즉시 + 재고확인, 예비기 1대 |

**검증**: 낙상 정밀도/재현율·오탐률(FP/시간), 심박 ECG 대조 오차, 모드전환 지연·정확도, 통합 end-to-end 알림 지연(<10초 목표: 도킹→낙상→알림).

## 10. Gazebo 시뮬레이션

**난점**: Gazebo(Gz Sim)엔 mmWave FMCW(micro-Doppler) 네이티브 센서가 없다(lidar·카메라·IMU·contact만).
**해법**: Gazebo는 시나리오의 물리·지상진실만 제공하고, **커스텀 "sim 레이더" 플러그인**이 실제 파이프라인과 동일 메시지를 합성 → 탐지 스택은 sim/real 무관.

- **월드(원룸 SDF)**: 벽·가구·바닥 + 충전 스테이션 + 행복이 로봇(URDF). **Human Actor(스켈레톤)**: 걷기·앉기·눕기·낙상(앞/뒤/옆)·장시간 무동작 스크립트 재생.
- **sim-radar 플러그인**: actor 링크 pose/velocity(GT)를 읽어 — 경로1(간단) 사람 위치·몸통속도·재실·미세움직임 → '사람 상태' 토픽 / 경로2(고급) 신체부위=점산란체 → 부위별 도플러 합성 → micro-Doppler 스펙트로그램 → 실제 CNN 입력. **도메인 랜덤화**(노이즈·클러터·체형)로 sim→real 갭 완화.
- **도킹·모드전환**: 스테이션 주행 → contact/proximity 도킹 감지 → 충전전류 boolean 시뮬 → 모드전환.
- **히어로 데모 완전 시뮬**: 도킹→전환→actor 낙상→sim레이더→CNN→이벤트→웹경보. **하드웨어 없이 end-to-end** → HW 리스크↓.
- ⚠️ Windows면 WSL2(Ubuntu)에서 ROS 2 + Gazebo.

## 11. Gazebo ↔ 웹앱 통신

```
Gazebo(Gz Sim) —gz topics→ ros_gz_bridge —ROS2→ [탐지: 낙상CNN·생체·고독사·모드전환]
   —이벤트/상태 토픽→ FastAPI(rclpy 구독) —WebSocket→ 웹앱(키오스크+대시보드)
                          └ REST·이벤트 DB, 알림 API(보호자·119)
   (옵션) Gazebo 카메라 —web_video_server(MJPEG)→ 대시보드 3D 뷰
```
- 표준 대안: rosbridge_server(WebSocket)+roslibjs로 웹이 ROS 직접 구독.
- **선택**: FastAPI가 rclpy 구독 → WebSocket 푸시(이벤트 저장·알림 릴레이 겸함). 단일 게이트웨이.

## 12. 노인 UI/UX — 직관적 메뉴·레이아웃

두 사용자·두 화면: ①어르신 대면(보행기 터치스크린=웹 키오스크) / ②보호자(성인 자녀, 폰·웹).

**어르신 UI 원칙(노인공학)**
- 큰 터치타깃 ≥72px·넉넉한 간격(오탭 방지)
- 큰 글씨 본문 ≥22–24px, **고대비 AAA(7:1)**, 따뜻한 색 — **노인 수정체 황변→파랑 인지 저하, 파랑-검정 조합 회피**
- 얕은 계층 1–2단, 화면당 선택지 최소(Hick), **제스처 금지·탭만**
- 아이콘+글자 라벨 병기, 자동 사라짐 금지, 되돌리기 관대
- **홈·SOS 고정 위치**(공간 기억), **음성 우선(TTS 읽기 + STT 명령)**

**어르신 홈**: 큰 시계·날짜 + 현재 상태 한 줄 + **큰 타일 4개 max**(🚶보행 도움 / ❤️건강 상태 / 📞가족 연결 / 🆘도움 요청). **충전(실내모드) 화면**: 정보 최소 "지켜보는 중" 안심 화면(큰 아이콘 + 심박·재실만), 상시 큰 SOS.
**보호자 대시보드**: 현재 모드 배지·실시간 상태 카드·이벤트 타임라인·활동/수면/심박 트렌드 차트·알림 이력.

## 13. 프론트엔드 — React + Vite (SPA)

> **v3 개정**: 실제 구현 = Gazebo 더미 데이터 → 웹 실시간 시각화. SEO·SSR 불필요 + roslibjs·Three.js·차트가 전부 JS 생태계 → **React+Vite SPA가 Next.js보다 가볍고 깔끔, Flutter보다 생태계 적합**(Flutter는 애니메이션 강하나 Dart·CanvasKit 번들·ROS 웹툴 우회 필요).

**스택**
- **Vite + React** (SPA, 키오스크는 PWA). 라우팅 React Router `/kiosk`·`/dashboard`.
- **Framer Motion**: 모드전환·화면전환 부드럽게
- **Three.js / PixiJS (Canvas·WebGL)**: 포인트클라우드·스펙트로그램 등 **고빈도 데이터는 `ref`+명령형 렌더**(React state 금지 — VDOM 재조정 우회)
- **Recharts / uPlot**: 돌봄진단 트렌드
- **Zustand + WebSocket 훅**: FastAPI 게이트웨이 실시간 스트림 / 이력·REST는 TanStack Query
- **Radix UI + 노인 디자인 토큰**: 접근성·22px/72px·AAA·따뜻한 팔레트 / 음성 Web Speech API·서버 STT·TTS 폴백

**성능 핵심**: "부드럽고 빠른 전환·효율적 처리"의 열쇠는 프레임워크가 아니라 **렌더링 전략** — 고빈도 스트림은 Canvas/WebGL 명령형, React는 저빈도 UI 껍데기만.
**경계**: Flutter=네이티브 모바일이 메인일 때 / Next.js=SEO·서버렌더 필요할 때. 둘 다 이 프로젝트엔 해당 없음.
